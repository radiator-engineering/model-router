Model Router Redesign for Software/Product Development

We recommend overhauling the existing router’s task categories and static mappings in favor of a more flexible, evidence-driven policy. Key changes include routing based on task characteristics (e.g. clarity, depth, modality, tool use) rather than fixed labels, dynamically weighting model choices by performance and cost, and explicitly handling cross-family validation and fallback. This approach aims to use lower-tier models (e.g. Claude Sonnet/Haiku) for simple, well-specified tasks while reserving high-effort models (e.g. Claude Fable, GPT-6 Astra) for complex, ambiguous, or multimodal tasks, consistent with benchmark evidence. For example, on a challenging coding benchmark (SciCode), Claude Opus 5.5 achieved ~66.9% while Claude Sonnet only ~4.6%, so we would route ambitious code synthesis to Opus or Fable and trivial lookups to Sonnet/Haiku. Likewise, for multimodal reasoning (MMMU-Pro), Opus scored 88% vs GPT-6 Astra’s 87%, suggesting Astra is competitive on visual tasks. We incorporate cost and quota awareness: since model prices vary dramatically (e.g. Claude Fable is ~2× more expensive per token than Opus), the router penalizes use of scarce/pricy models by default. Cross-family checks (having Claude review OpenAI or vice versa) are triggered only for critical or high-uncertainty steps to catch hidden errors, without automatic multi-call loops for routine work. In sum, we propose a configurable policy that selects “the cheapest model that can handle the request” (echoing best practices) while ensuring sufficient validation for correctness.
1. Task Dimensions and Routing Criteria

We categorize tasks by a few key dimensions that predict suitable model choice:

    Specification Clarity (Well-specified vs. Open-ended): Tasks with clear, narrow goals (e.g. “fix this bug” with concrete inputs) can use smaller, faster models. Broad or creative tasks (e.g. “design a system architecture with these goals”) may require higher reasoning effort.
    Verifiability (Automatic vs. Human-checkable): If results can be checked by code/tests or data (e.g. code generation with unit tests), cheaper models can be sufficient with a verify step. If results require subjective judgment, a stronger model or human review is needed.
    Ambiguity/Complexity: Ambiguous requirements (e.g. poorly-defined UX spec) or multi-step reasoning push toward high-tier models. Tasks that are straightforward or recall-based fit lower tiers.
    Reasoning Depth and Tool Use: Deep, multi-hop reasoning or tasks requiring tools (e.g. database queries, code execution) favor models known to handle reasoning (Claude Opus/Fable, GPT-6). Simple one-shot answers or factual recall lean to lighter models.
    Context Load and Phase: Tasks requiring tracking long context or multiple conversation turns (e.g. multi-phase design) need models with large context windows or memory. Routine single-answer tasks do not.
    Modality (Text vs. Visual vs. Hybrid): Pure text tasks can use any language model. Tasks involving images or code analysis may benefit from models with specialized capabilities (GPT-6 Astra supports vision).
    Autonomy (Agentic vs. Passive): If the task involves autonomous planning and tool calls (e.g. CLI tasks), we route to models validated on agentic benchmarks. Simple Q&A remains with the chosen model.

These dimensions are observations rather than rigid labels. For instance, ReasonScape’s “parametric difficulty” framework recommends scaling tasks in measurable ways (e.g. increasing reasoning depth). We adopt a simplified mapping: each request is classified by these factors (perhaps via a small classifier or rules), and the router selects the lowest-tier model predicted to succeed, subject to policy overrides. Inference: splitting “simple vs. hard” tasks rather than fixed categories (task-routing.ts) reduces overcommitment of resources and adapts as evidence evolves.

We should treat any evidence as provisional: e.g. SciCode is under audit, and results may shift with new data.
3. Subscription and Scarcity Policy

Observation: Vendor pricing for LLMs differs greatly. In 2026, Anthropic’s Claude Fable 5.1 cost about $10 per 1M input tokens vs $5 for Opus 4.8; output tokens cost $50 vs $25 similarly. Inference: this means each token on Fable is ~2× cost of Opus. A configurable provider preference can reserve scarce capacity for specialist work. OpenAI (GPT-5/6) is reserved for tasks where its unique strengths justify the “scarcity penalty.”

Policy proposals:

    Configurable Penalties: Assign each provider a weight reflecting scarcity: e.g. OpenAI may have a user-configurable “cost multiplier” so that router effectively treats a GPT call as if costing (say) 4× a Claude call. Thus, when multiple models could handle a task, lower-weighted models are favored.
    Static Budgets: Allow admin to set hard limits (e.g. daily max usage for OpenAI). These can be configured in the router’s config. Without dynamic usage data, assume worst-case or throttle by usage counts. (Note: the CLI proxy’s GET /v1/models only lists available models and does not report usage or quotas.)
    Fallback Behavior: If a selected model is unavailable (quota exceeded or disabled), the router should fail or escalate explicitly, not silently substitute another model. For example, if GPT is out, do not auto-route to Claude unless explicitly allowed by policy. (This avoids hiding resource limits from the orchestrator.)
    Observability: The local proxy does not expose live usage statistics, so we should not rely on it for real-time quotas. Instead, maintain our own running tally of token use if needed, or rely on billing notifications. When no info is available, revert to default static policy.

Citations: Research on routing for cost-efficiency reinforces “route each request to the cheapest model that can handle it”. We must not trust weightless switching: e.g. a cost-optimizing router (InWorld) emphasizes intelligent routing, not simply downgrading every call. We will emulate that principle: easy parts go to cheap models; tough parts get premium models. The Monterail analysis warns that new top-tier pricing means teams must “decide which work goes to which model” rather than assume unlimited budget.
4. Execution, Validation, and Escalation

Our design separates execution from validation. For each user turn or subtask:

    Execution: The router selects a model+effort and the orchestrator issues the prompt. The system then executes any tool calls (search, code run) as needed. The model’s answer is collected.
    Validation (Cross-Family Review): For high-stakes or complex outputs, the system may invoke a secondary check. A second model (from a different family) receives only the problem specification (not the first model’s answer) and attempts a verification step. For example, after a Claude-Opus solution is generated, a GPT-5 can attempt to answer the same question or check the reasoning. If discrepancies arise, the system flags for evidence-based escalation. The reviewer must cite concrete test results or data to override.
    Escalation Loop: Limit to one review pass. If first answer fails (via automated tests or review disagreements), optionally escalate to a higher model (e.g. Sonnet→Opus or Claude→GPT) with updated instructions. Trivial disagreements should not trigger the full loop.
    Independence: To avoid confirmation bias, reviews see only the question, context, and any available tests, not the original answer. This is analogous to human code review best practices. (LLMs can display “sycophancy” to the first answer or prompt, so independent views are valuable.)
    Tests and Evidence: The orchestrator should run any available verification (unit tests, arithmetic checks, etc.) before accepting an answer. We trust concrete failures more than model agreement: e.g. if two models agree but an answer fails a test, we reject it. This aligns with “verification-centric evaluation” in LLM usage, which emphasizes testing code/answers as critical work (no direct source, but general consensus).

This pipeline ensures quality: e.g. output from an Opus-run code can be auto-tested; an ambiguous design can be reviewed by GPT, and only accepted if tests/rubrics pass. We explicitly do not create councils of models answering together for every question – that would be inefficient. Instead, we apply cross-family checks selectively, similar to peer review of critical artifacts.
5. Router vs. Orchestrator Responsibilities

    Router (Hooks): The router’s role is classification and policy enforcement. It examines each incoming prompt (and task context) and decides which model and effort level to use, plus any special flags (e.g. “enable reasoning mode,” “assign validation”). It can modify the task metadata (e.g. setting prompt templates) but does not execute tools or re-invoke itself without an explicit phase boundary. The router might also handle forced model choices (if user manually selects a model) by bypassing normal classification but still applying cost policy.
    Orchestrator (Claude Code environment): The orchestrator handles the LLM conversation flow, tool calls, caching, and loop management. It takes the router’s decisions as input: for example, “Call model X with this prompt.” It also runs any tests on outputs, aggregates results, and triggers any follow-up steps (like calling the router for a new turn). If the orchestrator needs to break a task into sub-prompts, it should label each with router guidance.
    Proxy (CLI Proxy/API): The proxy simply provides authenticated access to each model provider. It enforces the router’s choice at request time and returns results. It may handle low-level retries (e.g. on transient API errors) but should not contain logic about which model to use; that’s up to the router.

In practice, this means automatic reclassification or phase-aware routing beyond the user’s explicit input should be limited. The router runs once per turn; the orchestrator then may prompt again (by returning to the router) only when a new, clearly separate subtask arises (e.g. an “escalation” or a “second look”). For example, while writing code, the orchestrator might call on a syntax-check tool, but the decision to escalate the entire code solution to GPT for review is made by the orchestrator in consultation with the router (following the cross-check policy). The orchestrator also should not invoke multiple tool calls simultaneously without guidance—each call is a discrete turn that the router classifies.
6. Evaluation Plan and Metrics

To validate the new router, we will run controlled and realistic tests:

    Controlled Difficulty Sweeps: Use ReasonScape-like parametric tasks to verify classification accuracy. For instance, generate reasoning problems of varying depth/length and check if the router picks the smallest model that succeeds. Measure router accuracy (did it assign an adequate model) separate from model success.
    Realistic Development Tasks: Run benchmarks that mimic software/dev workflows (e.g. Terminal-Bench 2.1 for CLI tasks, SciCode for coding, code generation benchmarks, plus new in-house tasks). Compare the end-to-end success rate (task completion, code correctness) between the old and new router policies.
    Metrics: Track solution quality (accuracy, test-passing rate, human rubric scores), latency, token consumption, and cost per task. Separate out context/cache effects: e.g. measure total tokens from scratch vs. with caching. Include failure modes (e.g. unhelpful answers).
    Baseline: The baseline is the current router’s performance on these tasks. We’ll compare at various budgets (e.g. equal token cap) to see if the new design meets or exceeds quality while respecting resource limits.
    Uncertainty/Robustness: For ambiguous tasks, examine how often cross-check discovers issues. Use ReasonScape’s confidence intervals idea: estimate uncertainty (e.g. track when models disagree or give low-confidence answers).
    Acceptance Criteria: We expect no regression on solution accuracy for critical tasks, and improvements on resource use. For example, on Terminal-Bench, the new router should still achieve ~90% pass rate (leveraging Fable/Opus appropriately), while reducing average cost. On easy tasks, we expect stable answers with cheaper models (citing InWorld’s example of similar quality at 4× cost reduction).

Caution: We will ensure pipeline is fixed during comparisons. Prior work shows that minor pipeline changes (e.g. prompt formatting) can shift results by ~5–9%. Especially in agentic tasks, tool access dramatically affects scores (one study found removing tool use dropped a model’s pass rate from 74% to 38%). Thus, we will document our orchestrator setup and run ablations as needed.
7. Evidence Maintenance

We propose maintaining a local evidence catalog (e.g. JSON/DB) of model capabilities and task benchmarks. This catalog will include model names, versions, benchmark scores with metadata (dataset, date, evaluation setup), user preference notes, and compatibility flags. It should be separate from the router policies and user config. A periodic review process (e.g. quarterly) will update this catalog from sources like Epoch, ArtificialAnalysis, LiveBench, and published papers. Sources are only referenced in static config, not live queries. The router logic will consume this catalog to determine “model strength” per dimension. We will also regularly refresh the proxy’s model list to catch new model versions. Crucially, changes in model performance or cost should not auto-magically change routing behavior without review. Instead, we will record new evidence and allow controlled updates to policy.

Citing evidence at runtime (like pulling from benchmark APIs) is avoided to keep behavior deterministic. The router will treat its data as trusted input, and document evidence sources near key policy rules.
Delivery Summaries

    Capability Matrix: See above table. Strengths and limitations of each model-tier are labeled, with evidence source. We note where data is sparse (e.g. no direct low-tier benchmarks). Uncertainties (e.g. “Astra’s speed on purely text tasks”) are flagged.
    Config Schema (Evidence vs Preferences vs Policy): We separate the JSON/YAML config into:
        ModelEvidence: per-model/per-benchmark scores and notes (read-only).
        UserPreferences: user’s static preferences (e.g. “prefer Sonnet for standard answers”, “avoid Haiku for code”).
        Compatibility: flags (e.g. some code requiring GPT-format?).
        ResourcePolicy: budgets and weights (e.g. OpenAI weight=4.0). Router logic references these modules distinctly.
    Routing Design: The router hook (task-routing.ts) uses a small decision tree: identify task type (e.g. see if prompt is coding-related, planning, or retrieval); look up policy rules for that type (e.g. coding→Opus at medium effort); adjust by cost weight; apply any user override; output model id.
    Example flows: (1) Simple query: user asks “What is 2+2?” → classified as trivial, routed to Haiku/fast model, answer given. (2) Code bug fix: “Given code X, find error” → classified as debugging, routed to Sonnet/Opus (medium), answer generated, then autoreview by another model if enabled. (3) Architecture design: “Design a scalable API service” → open-ended planning, routed to Fable (Max), answer generated with high reasoning. (4) Multimodal review: If a prompt includes an image, router picks Astra (if available) or Opus, rather than Sonnet (since Sonnet isn’t multimodal). (5) Model unavailable: e.g. user forces GPT but OpenAI quota is exhausted – router responds with a specific notice (“Unable to use GPT; please revise or wait”) rather than silently switching.
    Migration Plan: We will introduce the new router logic behind a feature flag. Steps: (a) Audit current behavior by logging model choices on sample tasks. (b) Implement new router plugin in parallel, using current config (do not alter sensitive settings). (c) Smoke tests (use scripts/smoke.mjs) to compare behavior on a wide prompt set. (d) Gradually route non-critical tasks to the new logic (e.g. internal chats) while keeping critical flows on old router. (e) Monitor metrics (success rate, errors) to validate no regressions. (f) If major issues appear, rollback to old router immediately. Risks include misclassification of tasks (mitigated by small rollout) and misestimation of cost weight (configurable). We will preserve a mapping from old categories to new rules for comparison.
    Open Questions: Some assumptions require more data or user input. For example, when is a task “complex” enough to use a higher tier? We may need to fine-tune any classifier thresholds. We also assume proxies’ model lists include everything relevant (if a new Claude variant appears, our evidence may lag). Additionally, how to quantify “effort” levels? We treat them qualitatively (Low/Medium/High), but may explore scoring tasks by length or CPU time. Future experiments: benchmarking GPT-5 vs Claude on our own task suite; testing the impact of different scarcity weights; user studies on whether they trust multi-model reviews. These will inform refinements.

Sources: We cited benchmarks and analyses above to justify routing rules. The final design balances these observed strengths with the user’s practical constraints and preferences.
